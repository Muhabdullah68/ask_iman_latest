Q-2 · Surah reading pane header buttons (Play Surah / English) can trigger RenderFlex overflow on narrow desktop widths
Location: surah_explorer_web.dart:483-499

The _PaneHeader renders a Row → Expanded → Column → another Row containing two _PillButtons with no Flexible/Wrap. At the same time the left side of that same column also contains a Row with a Wrap for chips and a Surah title column + arabic name Text on the right. When viewport width is 960–1050 px (the breakpoint where wide=true but internal reading pane width is still constrained to 600–800 px after 316 px sidebar + divider), the Play Surah / English buttons force the header Column wider than its parent and a second horizontal overflow appears. This is likely what pushed the reading list down by those 15 px in your screenshot as well.

Fix: Wrap the button row in Wrap(spacing: 10, runSpacing: 8, children:[…]) and remove the hard const SizedBox(width: 10).

🟠 HIGH — Will break (or already breaks silently) when used on web
Q-3 · just_audio_background imported in the web Quran audio service — web does not support it
File: quran_audio_service.dart:2

just_audio_background wraps Android/iOS foreground services, media sessions, and lockscreen controls. It has no web support (pub.dev "Web" column is blank / unsupported). The app still builds because AudioPlayer from just_audio is web-capable, but the moment any web user clicks Play Surah / Play Ayah:

AudioSource.uri(..., tag: MediaItem(…)) → the MediaItem class itself comes from just_audio_background, not just_audio. At runtime on the web, MediaItem import either:
throws UnimplementedError inside just_audio_background's native channel bridge, silently swallowing the exception (line 69–74 catches everything), OR
more commonly in recent versions, the whole setAudioSource() future never completes — so the button appears to do nothing, and QuranAudioBar never animates in because currentId was set before the try/catch but isPlaying stays false.
This is the #1 hidden "why doesn't audio work on web" bug.

Fix (two options, pick one):

Option A — minimal: Make MediaItem import conditional. Create a simple kIsWeb wrapper that assigns a plain tag: Object() (or use just_audio's AudioSource.uri(..., headers: …) without a tag) on web, and only construct a real MediaItem on mobile.
Option B — clean: Remove the just_audio_background import entirely from Quran audio service and import just_audio only. Add a separate optional mobile-only audio_service-based background manager that is never imported into the web compilation unit via conditional imports (import 'stub.dart' if (dart.library.html) 'web.dart' if (dart.library.io) 'mobile.dart').

Q-6 · Sidebar Arabic surah name width overflows tile in 316-px rail
Location: surah_explorer_web.dart:_SurahTile

The arabic name is a Text at the end of a Row with unbounded width. When you have a narrow sidebar (316 px) and a long Arabic name + a Flexible left column with "THE COW · 286 āyāt", the Arabic word pushes past the tile right edge and renders on the mint background of the reading pane (you can see it faintly for Al-Fātihah / الْفَاتِحَة on the right side in the screenshot — text is actually wider than the sidebar's 316-px container when the selected-tile gold badge + circle make it tighter).

Fix: Wrap the Arabic Text in Flexible(child: Text(…, maxLines:1, overflow: TextOverflow.ellipsis)), or better, use ConstrainedBox with BoxConstraints(maxWidth: 84) since Arabic surah names rarely exceed that width.

Q-7 · Juzz Grid shrinkWrap: true + NeverScrollableScrollPhysics inside SingleChildScrollView (QuranPaneScaffold) renders all 30 cards eagerly even in a long scroll view
File: juzz_web.dart:81-95

This is not a crash, but GridView.builder + shrinkWrap: true defeats the "builder" lazy-loading — all 30 _JuzCards with gradient decorations are laid out at once. Not severe at 30 items, but combined with 4 Image.network assets and syncfusion_flutter_pdfviewer (still in pubspec) on slower machines it contributes to a ~500 ms jank when switching into the Juzz tab.

Fix: Keep the pattern but replace shrinkWrap builder with a SliverGrid in a CustomScrollView, OR accept shrinkWrap and reduce gradient/box decorations to static colors.

Q-8 · syncfusion_flutter_pdfviewer declared in pubspec but never used in the Quran web stack → 6+ MB of extra web JS + license warning
Pubspec: pubspec.yaml:41 syncfusion_flutter_pdfviewer: ^28.2.12

Only usage in the project: pdf_viewer_screen.dart:64 — SfPdfViewer.asset()/file()/network() — a mobile-only screen (it uses asset: assets/pdf/surah_pdfs/… and file() paths).

On web, Syncfusion PDF has these consequences:

Adds 3–8 MB of canvas/skia-shimmed JS for a feature no web route uses.
Produces a "Syncfusion License Key Missing" banner overlay if/when the viewer is ever instantiated on web without key — since none of the web pages do this yet, it's latent.
Tree-shaking can't eliminate the plugin entirely because its method channels remain registered.
If you never intend a PDF-mode Quran on web, move syncfusion_flutter_pdfviewer behind a dart.library.io conditional import and remove it from the default web compilation.

Q-9 · ScaffoldMessenger.of(context) in DailyAyahWeb may return null inside QuranPage → GoRouter shell
Files: daily_ayah_web.dart:41-46 and daily_ayah_web.dart:51-53

Route tree: Scaffold (inside WebShell) → Expanded → QuranPage → Expanded → IndexedStack → QuranPaneScaffold → SingleChildScrollView → DailyAyahWeb. The context used is inside the Scaffold, so ScaffoldMessenger usually finds it. However GoRouter 16.x navigator rebuilds sometimes lose ScaffoldMessenger inheritance in shell routes — especially when navigatorKey (line 59 of web_router — AlarmService.instance.navigatorKey) is a different key than the default MaterialApp.router navigator. If snackbars silently don't appear in prod, this is why.

Fix: Wrap snack bar calls in a guard and/or use the root ScaffoldMessenger via ScaffoldMessenger.maybeOf(context, rootOverlay: true) ?? ScaffoldMessenger.of(context).
